# 联邦式中枢：一个 Agent，多个执行面

> **一句话**：入口平台负责"人跟 Agent 说话"，执行面负责"事情真正落地"。
> 两者解耦 —— 在企微里说一句话，Agent 可以到钉钉里查待办、到飞书里改文档、到板子上放首歌。

---

## 一、三层模型

```
        入口（人）
   ┌──────┬──────┬──────┐
  企微    飞书    Slack
   │      │      │
   └──────┴──┬───┘
             ▼
     内核（本项目）            队列 / 会话 / 审批闸门 / 模型热切换 / 分片
             │
             ▼
     一个 Agent（Claude Code） 决定用哪个执行面、调用哪个工具
             │
   ┌─────────┼──────────┬─────────────┬──────────────┐
  本机        P4 设备     钉钉工作区      飞书工作区
  Bash/文件   MQTT        dws             lark-cli
```

**内核不认识"钉钉"或"飞书"**。它只做四件事：排队、记住会话、**拦住危险动作**、决定用哪个模型。
选哪个执行面，是 Agent 根据用户的话自己判断的 —— 这也是为什么它是"联邦"，不是"网关"。

---

## 二、为什么不是"MCP 服务"或"又一个通道"

| 方案 | 问题 |
|---|---|
| 再写一条钉钉/飞书聊天通道 | 官方 CLI 已经覆盖（`dws` / `lark-cli`），重复造轮子且维护成本归我们 |
| 把官方能力包成 MCP Server | 多一层进程、多一套协议；官方 CLI 本身已经是"给 Agent 用的结构化命令 + Skills" |
| **直接用官方 CLI + Skills** | ✅ 零适配层：Agent 会 Bash，就能用官方能力；升级跟着官方走 |

官方 CLI 已经把"给 Agent 用"这件事做完了：结构化输出、`--dry-run`、`SKILL.md`。
本项目要做的是**加上它们没有的那一层**：审批、身份边界、跨平台路由约定。

---

## 三、身份边界（最重要的一条）

**入口身份 ≠ 执行身份。**

- **入口身份**：谁在跟你说话。本项目用白名单（企微 `userid` / 飞书 `open_id` /
  Slack member ID）把关，留空即拒绝启动。
- **执行身份**：这件事以谁的名义做。
  - 本机命令：这台机器的当前用户；
  - P4：MQTT 双向证书里的 `win-agent` 身份；
  - 钉钉 / 飞书工作区：**官方 CLI 的 OAuth 登录身份 —— 也就是你本人**。

所以，Agent 在钉钉里发的一条消息，**同事看到的是你发的，不是机器人**。
这是"借力"的代价，也是它的价值。规则：

1. **写操作必须让人看见执行身份**。审批卡上要写明「将以 `你的钉钉账号` 执行」。
2. **凭据不搬家**。`dws` / `lark-cli` 的 token 由官方 CLI 自己加密保管
   （`dws`：PBKDF2 + AES-256-GCM，密钥绑设备；`lark-cli`：系统 Keychain）。
   **不进本项目的 `.env`、不进日志、不进公开仓。**
3. **不跨账号猜身份**。多组织/多账号时，目标账号必须显式指定，不允许"用最近一次登录的"。

## 四、审批策略：读放行，写弹卡

| 动作 | 例子 | 策略 |
|---|---|---|
| **读** | 查待办、搜文档、看日历、搜人 | ✅ 可以直接执行（不弹卡） |
| **写** | 发消息、建待办、改表格、审批、建文档 | 🚨 **必须弹卡**，卡片写明平台/目标/动作/执行身份 |
| **未知** | 没在策略表里的命令 | 🚨 **按写处理**（fail-closed） |

⚠️ **"读"的边界要按平台各自定**，不能一刀切：有的接口名字像读、实际会改状态
（例如"标记已读"、"撤回"）。策略表里只收**真的无副作用**的子命令。

**当前状态（2026-11-10）：按命令判，不按工具判。** `Bash` 里的跨平台命令分三种处理：

| 判定 | 结果 | 依据 |
|---|---|---|
| **读** | 直放 | 官方 CLI 自己发布的契约：`effect=read` 且 `confirmation=not_required`（`dws` 已有 720 条） |
| **写 / 危险** | 弹卡 | `effect=write` / `destructive` |
| **表外 / 拿不准** | 弹卡 | 官方表里没有、含命令替换或重定向、多段里任意一段不过 —— **一律按写** |

读也不是无条件放：除官方契约外还有两道护栏 —— **本地写法检查**（命令替换、重定向、
环境变量前缀、管道）和**人工标注的敏感读**（读出来的是密钥，仍然弹卡，卡面写明）。
细节与逐项理由见 [`../interop/dingtalk.md`](../interop/dingtalk.md) 的「只读白名单」。

**表跟着官方走**：快照由 `tools/dws_effect_sync.py` 从 `dws schema --all --compact`
生成、入库、可 diff；`dws` 升级后跑 `--check` 看漂移。我们不维护"哪些是读"这张表 ——
官方维护，我们只读它的答案，再留一道自己的否决权。

**有一类路径不走弹卡，直接拒绝。** CLI 的令牌存储（主目录下的 `.dws` / `.lark-cli`、
本仓自己的 `data/wecom-cli-cc/`）不是"读"，它没有需要人判断的余地 —— Agent 没有正当理由
去读它们，所以命中就拒绝，连卡片都不发。这条规则**与审批开关无关**：没开审批也生效，
免卡白名单里的人也不能破例。细节见 [`../interop/dingtalk.md`](../interop/dingtalk.md) §2.4。

**谁需要点卡，按发消息的人分。** `CC_APPROVAL_AUTO_USERS` 里列出的 userid 不弹卡，
其余一律弹卡（群聊、私聊同一套）。旧开关 `CC_APPROVAL_DM`（私聊全自动）已废弃。

## 五、现在有什么 / 还没有什么

| 执行面 | 载体 | 状态 |
|---|---|---|
| 本机 | Bash / 文件工具 | ✅ 一直在用 |
| P4 平板 | `p4ctl`（MQTT 双向 TLS） | ✅ 已验收（六个动词） |
| 钉钉工作区 | `dws`（官方） | ✅ 已验收：读 + 写各一条（2026-11-10，全部经审批闸门） |
| 飞书工作区 | `lark-cli`（官方） | ⏳ 待接入 |
| Slack 工作区 | Slack Web API | — 暂不做（官方没有同等的工作区 CLI；只当入口） |

**没打勾之前不写"支持"** —— 这条和平台页里的「待实测」是同一个纪律。

**第一条要打勾的路：企微进，钉钉出。** —— ✅ **2026-11-10 已跑通。**

```text
企微群：「帮我看看钉钉待办里今天有什么」
  → 桥把这句话交给 Agent → Agent 决定用 dws
  → 审批卡：身份「钉钉 · 你的账号（不是机器人）」 + 要执行的命令
  → 点「允许」→ 结果回到企微同一个气泡
```

| 环节 | 实测 |
|---|---|
| 读 | 10 张卡 / 10 允许 / 0 拒绝，`rc=0`，结果回到群气泡 |
| 写 | 让 Agent 建一条带截止时间的待办：2 张卡 / 2 允许；**钉钉侧创建时间落在两次点击之间**，截止时间与用户原话逐字对上 |
| 卡面身份 | 用户目视确认「身份：钉钉 · 你的账号（不是机器人）」 |

每一步的验收判据在 [`../interop/README.md`](../interop/README.md) 的「接入六步」，
细节与原始数字在 [`../interop/dingtalk.md`](../interop/dingtalk.md) 的实测记录。

## 六、接一个新的执行面，要回答的四个问题

1. **它是谁的 CLI？** 官方维护 / 社区 / 自建。官方优先 —— 升级和协议漂移不归我们。
2. **它用什么身份执行？** 机器人 / 用户 OAuth / 应用 token。写清楚，别让用户猜。
3. **哪些是读、哪些是写？** 列一张子命令白名单；表外的按写处理。
4. **它怎么被 Agent 发现？** Skills 目录（`~/.claude/skills/…`）还是项目内 `CLAUDE.md`？
   优先 Skills —— 一次安装，所有入口平台的所有会话都能用。

## 七、边界与残余风险

三条用户必须知道 —— 它们**不会因为项目做得好而消失**：

| 风险 | 为什么消不掉 | 我们怎么压住 |
|---|---|---|
| **以你的名义执行** | 官方 CLI 用的是你的 OAuth —— 这就是"借力"的代价 | 写操作一律弹卡，卡面写明执行身份 |
| **误操作** | 命令面有几百条，"读"和"写"的边界每个平台还不一样 | 策略表外一律按写处理（fail-closed） |
| **数据外发** | 一句话就可能把 A 平台的内容发到 B 平台 | **不做自动跨平台转发**，必须由人开口 |

还有一条不是风险，但要先说清：**执行面是官方维护的**，它的命令面、鉴权方式、限流都可能变。
这不是缺陷 —— 我们选它，正是为了不替它维护这些。真变了，改这一层的文档和闸门表，**内核不动**。

---

## 八、不做什么

- **不再写任何聊天平台的传输通道**，除非官方确实没有（Slack 这类）。
- **不把官方 CLI 的凭据纳入本项目的配置体系**。
- **不承诺"任意平台任意能力"** —— 只承诺「已验证」那一列。
- **不做跨账号的隐式路由**：多组织时目标必须显式。
