# 锚点与增量：为什么这个仓可以被「取长补短」

> 这篇讲的不是代码怎么工作，而是**这个仓打算怎么被别人使用**。
> 也正因为如此，它本身是开源的 —— 你可以照这套逻辑做你自己的项目。

---

## 一、一句话

**本仓不要求你全量覆盖，也不绑定某一家的固定实现。**

它提供两样东西：一条**可机械判定的边界**（哪部分是你的、哪部分是它的），
和一套**增量吸收的流程**（发新版时只吸收你要的，不丢你改的）。

---

## 二、两种人，两条路

| 你是谁 | 你要做的事 | 走哪条路 |
|---|---|---|
| **新用户** | 从零搭一套「聊天入口 → 本机 Agent」 | 照 [教程](claude-code-wecom-guide.md) 从零接入。**你已经验证过三次**：OpenCode、Codex、DSH 三个互不知情的 Agent 各自照着同一份文档接上了 |
| **已定制的老用户** | 上游发了新版，想吸收又不丢自己的改动 | 走 [升级与取长补短](UPGRADING.md)：哈希树对比 → 只看删除行 → 整份替换或定点合并 → 验证 → 回归 |

两条路都是**让执行者的 Agent 自己去做**，不是"下载一个包，点下一步"。
本仓的读者本来就不是"装软件的人"，而是"有 Agent 的人"。

---

## 三、为什么不必全量覆盖

因为边界是分开的，而且**分层不是口号，是被检查的**：

| 层 | 2026-11-12 的企微适配 | 换 harness 时要动吗 |
|---|---|---|
| 平台层 `app/platforms/wecom/` | 6 个文件 ~49 KB | 不动 |
| 内核 `app/core/` | `bridge_core.py` ~81 KB | 不动 |
| 契约 `app/core/contract.py` | ~2.6 KB | 不动 |
| 运行器 / harness 适配 | `app/core/runner.py` 或你自己的 `<x>_runner.py` | **只有这里动** |

`tools/check_layers.py` 守着这条线：内核里不许出现平台专属的帧名字、错误码、WebSocket。
**它是"约定"能变成"事实"的原因** —— 没有检查，边界过两个版本就会自然腐化。

---

## 四、它已经有过的证据

**接入：三例。** OpenCode / Codex / DSH，各自从零、互不知情，
其中 4 个适配点长成了同一个形状 —— 这不是我们总结的规律，是它们各自撞出来的。
详见 [外部接入记录](field-reports/README.md)。

**回灌：一例，而且是一个闭环。** 2026-11-12：

1. DSH 报问题（同机多套桥的两个系统级名字没隔离）；
2. 本仓做成 `BRIDGE_INSTANCE`，并比提议多守三处，发布；
3. 它的 Agent 把新版收回去：**76 个共有文件只有 5 个不同**，
   `common.py` 是 +55/−0 的纯增量 ⇒ 整份替换；`bridge.py` 定点合并 4 处；
4. **它自己的六个适配点、进度帧、熔断、原生打断，一处没丢**；
5. 同一次它还回灌了我们两条缺陷（图片提示写死 `Read`、README 无条件承诺"会看图"），
   两条都改了。

那一步的结论是它自己写的：

> 平台层、内核、契约**一行未改**。换的是「大脑」，身体没动。

## 五、这个模型成立的三个前提

少一条，它就会退化成"又一个会烂掉的 fork"：

| 前提 | 不成立会怎样 |
|---|---|
| **边界被检查**（`check_layers.py`） | "分层"变成口头约定，两个版本之后谁也不敢动 |
| **差异可分类**（发布时给文件分类表） | 每个下游都要重新做一遍判断，做错一次就"红了但没坏" |
| **高风险步骤有人**（整份替换 / 定点合并 / 不抄测试） | 自动化把"看起来成功"当成"真的成功" |

⇒ 所以：**我们不把它写成"全自动同步"。** 准确的描述是
「**步骤与判据都写清楚了，你的 Agent 能照着做；决定性的那几步留给人点头**」。

## 六、我们对下游的义务

这套模型有一个不对称：**上游不修的小毛病，下游就不敢修。**

DSH 在同步记录里把 `codec.py` 的多 `@` 残留列为"不修"，理由不是"它不重要"，
而是「**修了本副本与发布仓不一致**」。这句话反过来就是对我们说的：

> 一个"待决策"挂着不处理，等于在每个下游身上加一道同步成本。

⇒ 所以"让锚点值得回"不是情怀，是维护义务，具体有三条：

1. **把待决策清掉**，尤其是那种"改起来很便宜、但会让下游分叉"的；
2. **每个发布点给一张文件分类表**（[格式见 UPGRADING](UPGRADING.md#五发布方该给的文件分类表)）；
3. **文档写能力口径，不写我们的实现口径** —— 例如"图像理解取决于模型能力"，
   而不是"它会用 `Read` 看图"。

## 七、回退：诚实地说是"还没有"

一套"可以随意试错"的模型，必须有一个**真的能回去的地方**。

> ⚠️ **当前没有发布级回退点。** v1.0.0 之前本仓不打 tag；
> 想留退路请自己开分支 / fork。**自 v1.0.0 起**每个发布点一个 tag，回退就是一条命令。

这条不写成"已提供"，因为写了却做不到，比不写更糟。

## 八、它证明了什么，没证明什么

| | |
|---|---|
| ✅ 证明了 | 换掉运行器之后，平台层 / 内核 / 契约**可以一行不改**（三例接入 + 一例回灌） |
| ✅ 证明了 | 一次完整的版本跨越，下游的改动量可以是**几个文件**（76 → 5） |
| ✅ 证明了 | 上游的缺陷可以由下游的实测回灌修掉（2026-11-12 两条） |
| ❌ 没证明 | 大量用户、多个版本之后仍然如此 |
| ❌ 没证明 | "自动同步" —— 目前只到"Agent 能照着做 + 人把关" |
| ❌ 没证明 | 联邦式执行面那一半（见下） |

---

## 九、和「联邦式中枢」是什么关系

两条**互相独立的轴**，别混在一起：

| | 回答什么 | 在哪 |
|---|---|---|
| **本文** | 别人怎么**接**进来、怎么**更新** | 分发模型 |
| [联邦式中枢](federation.md) | 一个 Agent 怎么**用多个执行面**（钉钉 / 飞书 / 本机 / 端侧设备） | 内部结构 |

前者不依赖后者：你现在就可以 fork 一份，只保留企微入口。
后者也不依赖前者：执行面的增减，和"要不要跟进上游"没有关系。

两者合起来才是完整的一句话：**入口可以换、执行面可以加、版本可以增量吸收。**
