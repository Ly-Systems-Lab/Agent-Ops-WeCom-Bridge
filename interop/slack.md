# Slack · 入口有，执行面暂时没有

**状态：本项目在 Slack 上只做入口，不做执行面。**

> 入口那一层（Socket Mode、审批卡、线程续聊、24 小时连续运行）在
> [`platforms/slack/`](../platforms/slack/README.md)，已真机验收。

---

## 1. 官方给了什么

- 官方提供 **SDK / Events API / Socket Mode / Web API** —— 这些是"怎么写一个 Slack App"的原料。
- 截至本项目核对时，**没有找到与 `dws` / `lark-cli` 对等的「工作区操作 CLI」**：
  没有一个装完就能让 Agent 直接"查频道、发消息、该表格、看审批"的命令行工具。
  如果官方后来出了，以官方为准 —— 这一页就要改写。

⚠️ **不要把"有 App 开发工具"当成"有工作区 CLI"**：前者帮你把 App 部署上去，
后者才是 Agent 直接用的那只"手"。这是两件事。

## 2. 现在怎么用

**没有官方 CLI ⇒ 执行面要么自己封装 Web API，要么就不做。**

当前选择是**不做**：

| 方案 | 代价 |
|---|---|
| 自己封装 Web API 当执行面 | 我们要替 Slack 维护一套命令面、参数、错误码 —— 与"能力分层，别重复造轮子"相冲突 |
| 等官方出 CLI | 现在没有，不承诺时间 |
| 只做入口 | ✅ 现在这样：**在 Slack 里说句话，Agent 去钉钉 / 飞书 / 本机干活** |

也就是说：**Slack 可以当"入口平台"，暂时不当"执行面"。**
这正是联邦式中枢要解耦的那件事 —— 两者本来就不必是同一家。

## 3. 如果将来要接

按 [接入六步](README.md#三接入六步对任何官方-cli-都一样) 走，先回答
[四个问题](README.md#五接一个新执行面先回答四个问题)：

1. 它是谁的 CLI？（官方 / 社区 / 自建）
2. 它用什么身份执行？（Bot Token / User Token —— 这两个的可见范围差很多）
3. 哪些是读、哪些是写？（Slack 的 `chat.update`、`reactions.add` 都算写）
4. 它怎么被 Agent 发现？（Skills 还是项目内说明）

⚠️ **一条已经实测过的差异**：Slack 没有官方的流式消息接口，只能反复 `chat.update` 同一条，
约 **1 次/秒/频道** —— 所以本项目给它打了 ⚠️ 而不是 ✅（见
[platforms/README.md](../platforms/README.md)）。这一条会直接影响将来执行面的节流设计。
