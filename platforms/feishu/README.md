# 飞书（Lark）

**状态：真机验收通过 —— 私聊流式气泡、群聊审批卡、拒绝即终止、卡片排队、超过 1 分钟的长任务，
五项都跑过（2026-11-05）；随后又验了稳定性：连续在线 24 小时零断线，断网 10 分钟能自己回来（2026-11-07）。**

飞书是目前四个平台里**形态最接近企业微信**的一个：长连接是官方一等公民，
流式更新有专门接口，卡片回调也能走长连接。按契约的四条能力轴，它四条全过；
换到飞书之后，人 ⇄ Agent 的调度方式一条都没改，变的只有消息从哪来、卡片长什么样。

---

## 它的形态

| 能力 | 飞书的做法 |
|---|---|
| **① 长连接** | 官方提供「使用长连接接收事件」与「使用长连接接收回调」两种模式，SDK 主动外连，不需要公网地址或域名 |
| **② 可更新消息** | CardKit 流式卡片：建卡时开 `streaming_mode`，之后逐帧改元素内容，最后关流收口 |
| **③ 交互卡片** | Card 2.0 + 卡片回调；回调经**同一条长连接**回来，还能在响应体里就地改卡 |
| **④ @ 隔离** | `im.message.receive_v1` —— 群里只有 @ 机器人的消息才会推给应用 |

---

## 8 个适配点，它的答案

| # | 适配点 | 答案 |
|---|---|---|
| 1 | 建连与重连 | 官方长连接 `wss://msg-frontier.feishu.cn/ws/v2`；SDK 自带重连，外层再加一层进程级看门狗 |
| 2 | 收消息 + @ + 去重 | `im.message.receive_v1`；按 `message_id` 去重。群聊 @ 在正文里是 `@_user_1` 这类**占位符**，要靠 `mentions[].key` 映射回去 |
| 3 | 发消息 + 更新同一条 | CardKit 流式；**普通文本消息不能原地更新，流式必须走卡片**。三步：建卡开流 → 以 `card_id` 发消息 → 逐帧改元素 → 关流 |
| 4 | 发卡片 + 规格限制 | Card 2.0；按钮文字实测 **≥12 个汉字无换行、无截断**（只验到 12，没压到天花板） |
| 5 | 收卡片回调 | `card.action.trigger` 经同一条长连接回来，`action.value` 原样带回。**回调响应里挂一张新卡就当场生效**，点一次按钮即消失 |
| 6 | 分片与错误码 | 单条 content ≤ 150 KiB；**被 `230025` 拒了才切**，不预判 |
| 7 | 身份与白名单 | `open_id`（应用内唯一），**留空即拒绝启动**（fail-closed） |
| 8 | 限流与节流 | 保守 5 条/秒；`230020`（chat rate limit）一律**退避重试，不当失败** |

## 换平台必须知道的六条（前四条实测过，后两条是文档级约束）

1. **单条消息体积差 7.5 倍。** 飞书 content ≤ **150 KiB（153,600 B）**，企微是 20,480 B。
   实测 153,000 B 通过、153,600 B 被 `230025` 拒绝。
   ⇒ 分片阈值**必须按平台重算**；照搬企微的数字只会把消息切得毫无必要地碎。
2. **流式的限制换了一个维度。** 企微卡的是"一次能发多少字节"，飞书卡的是"**多快能改一次**"——
   实测单次改元素约 0.4 s，加上间隔实际约 **2 帧/秒**。
   ⇒ 这两个数不能互相推算；进度刷新上到飞书必须**为频率单独节流**，否则帧会排队、越推越滞后。
3. **按钮文字的上限刚好相反。** 企微只有 2 个汉字的余量（4 个字会被截成「清...」），
   飞书 12 个汉字照样完整显示。⇒ 照抄企微的口径，会把飞书的按钮无谓截短。
4. **身份口径不一样。** 企微的 `userid` 是全局稳定的；飞书的 `open_id` **应用内唯一** ——
   实测**跨应用版本发布仍然稳定**（换头像触发过一次发版，`open_id` 逐字符不变），
   但**换 `app_id` 之后白名单要重填**。这两件事必须分开说，不能含糊成"稳定"。

下面两条没在真机上撞到，因为一开始就照着做了 —— 但反过来做会很痛：

5. **长连接只支持企业自建应用。** 想走"自建应用 + 长连接 + 免公网"这条路，应用类型不能选错。
6. **流式只对富文本组件生效。** 官方写明流式仅支持富文本元素 —— 卡片模板一开始就要按富文本搭，
   事后回头改等于重做整套卡片。

---

## 一条运维硬约束

**同一个应用的多条长连接是「分摊事件」，不是广播。** 两个进程同时连的时候，
消息和卡片回调会**随机落到其中一条**上 —— 现象是"点按钮好几次才消失"，
因为一半的点击被投给了另一个进程。

⇒ 飞书适配器**必须有单实例锁**。排查"事件时而收到、时而收不到"时，先数长连接数，别先怀疑权限。

**断线后的恢复窗口由服务端决定，调用方改不了。** SDK 的重连参数（间隔 120 秒、外加最多 30 秒
随机抖动）来自建连握手时下发的配置，且明确不对外开放覆盖 ⇒ 网络中断一次之后，
**最长大约两分半收不到消息**才会恢复。这不是"卡死"，也不该在调用方另造一套秒级重连；
上层要按这个尺度设计自己的超时与重试。

## 待实测（没打勾之前不写"支持"）

- [x] Card 2.0 的按钮回调能**走长连接**收到 —— `action.value` 原样返回，同时拿得到 `operator.open_id`
- [x] 回调响应里就地改卡 —— 返回 `card: {type:"raw", data:<新卡>}`，点一次即生效
- [x] 按钮文字的实际长度上限 —— ≥12 个汉字无截断（未压到天花板）
- [x] 单条消息的字节上限与超限错误码 —— 150 KiB / `230025`
- [x] 推送频率上限 —— 均匀 ≤12 条/秒零失败；8 线程并发 80 条只过 32 条，其余 `230020`
- [x] 群聊不 @ 是否推消息 —— 不推（与企微同构）
- [x] 含多次工具调用、超过 1 分钟的长任务 —— 实测 100.3 秒、3 次工具调用，
      期间 3 张审批卡一张一张出现
- [x] `/new` 之后模型拿不到上一轮的**对话内容** —— 下一条命令不再带 `--resume`，Session 是新的
- [x] 顺带一条边界：`/new` **不会**清掉模型自己写到磁盘上的东西。
      它清的是上下文，不是信息源 —— 这一点每个平台都一样，要单独验
- [x] 长连接连续运行 24 小时、断网后能自愈 —— 连续在线 **24 小时 05 分零重连**
      （每 5 分钟采一次，全程在线率 100%）；断网 10 分钟，网络恢复后约 **1.5 分钟**自己连回，
      期间进程不退出、不需要人工干预
