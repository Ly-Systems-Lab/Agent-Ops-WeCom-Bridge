# 平台适配

**同一个内核，不同的聊天平台 —— 约定不变，实现各答一遍。**

这个项目要解决的问题从来不是"企业微信"这四个字，而是：

> **人不在电脑前的时候，怎么找到并驱动那台机器上的 Agent。**

企业微信只是我们跑得最远的那个入口。这一节把「换一个聊天平台要重答哪些问题」摆出来 ——
按 [平台适配契约](CONTRACT.md) 的 8 个适配点，每个平台各填一份答案。

---

## 为什么值得把这件事做出来

一套约定如果只能跑在一个平台上，那它就不是约定，是那个平台的实现细节。

判断"它是不是真的平台无关"，标准只有一条：

> **换一个平台，人 ⇄ Agent 的调度方式要不要跟着变？**

如果五条约定不变、交互基准不变、否决权的位置不变，变的只有"消息从哪来、卡片长什么样" ——
那这套东西才配叫底座。

---

## 四个平台，四条能力轴

| 平台 | ① 长连接 | ② 可更新消息 | ③ 交互卡片 | ④ @ 隔离 | 状态 |
|---|---|---|---|---|---|
| [企业微信](wecom/README.md) | ✅ | ✅ | ✅ | ✅ | **参考实现**：真机验收 + 两次外部 Agent 独立复现 |
| [飞书](feishu/README.md) | ✅ | ✅ | ✅ | ✅ | **已实现并真机验收**（2026-11-05） |
| [钉钉](dingtalk/README.md) | ✅ | ✅ | ✅ | ✅ | **不重复实现**：官方 `dws` 已覆盖通道层，本项目把它当执行面接入 |
| [Slack](slack/README.md) | ✅ | ⚠️ | ✅ | ✅ | **已实现并真机验收**（2026-11-07）；24 小时连续运行（进程零重启） |

**"能力已核实"的含义要说清楚**：它是**对照官方文档逐条确认过接口形态**，不是跑过。
每个平台页里都单列了「待实测」一节 —— 那几项没打勾之前，我们不写"支持"。

> Slack 的 ⚠️ 不是"不能更新"，是**没有官方的流式接口**：只能反复 `chat.update` 同一条，
> 而它大约 1 次/秒/频道 —— 能做的，但必须节流。详见它的页面。

## 一句话

**平台是入口，不是身份。**

同一个 Agent 从企微进来、从飞书进来、从 Slack 进来，都是同一个"工作区 + 记忆 + 大脑" ——
换的只是窗口，不是人。
