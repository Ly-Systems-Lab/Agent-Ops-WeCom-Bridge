# Slack

**状态：能力已核实（对照官方文档与限流资料），适配器未实现。**

Slack 是四个平台里**技术门槛最低、工程约束最明确**的一个。
它唯一的短板是 ②：没有官方的流式接口 —— 但我们的推送策略本来就是"变化才推"，正好对得上。

---

## 它的形态

| 能力 | Slack 的做法 |
|---|---|
| **① 长连接** | **Socket Mode**：应用主动外连，不需要公网地址；用 app-level token 建立连接 |
| **② 可更新消息** | ⚠️ **没有官方流式接口**：靠 `chat.update` 反复改同一条消息 |
| **③ 交互卡片** | Block Kit + interactivity；Socket Mode 下回调也走 WebSocket |
| **④ @ 隔离** | `app_mention` 事件 —— 只有 @ 应用的消息才推 |

## 它唯一真正的工程约束：限流

`chat.update` 大约每秒一次、按频道计。这意味着**逐字流式在这条路上不成立**。

但这恰好不构成问题，因为我们的"真进度"从来不是逐字推送 ——
本来的策略就是**变化才推 + 60s 兜底心跳**。换到 Slack 只需要把节流参数调到 500ms~1s。

> 反过来看，这是一次有用的验证：如果一套设计只能在"不限流的平台"上成立，
> 那它本来就不够稳。**限流是压力测试，不是障碍。**

---

## 与企微的差异（动手前必须知道）

1. **消息历史与检索有额外限制。** 公开资料提到非 Marketplace 应用的 `conversations.history` /
   `conversations.replies` 可能被限到很低的频率与条数 —— **这一条来源不是官方文档，必须自己核实**。
   它直接影响"桥能不能回头读上下文"这种设计，所以要先验再定。
2. **英文生态。** 文档、社区、错误信息全是英文；排查时少了中文资料这一层缓冲。
3. **免费版 workspace 有自己的历史与消息保留策略**，做长期常驻测试前先确认它不会干扰结论。
