# 钉钉

**状态：能力已核实（对照官方文档逐条确认），适配器未实现。**

钉钉和飞书是同一档：长连接、流式卡片、卡片回调都有。
它有一处比飞书更干净 —— **一份 Stream 连接同时收机器人回调、事件订阅和卡片回调**，
不用为了卡片回调另开一条路。

---

## 它的形态

| 能力 | 钉钉的做法 |
|---|---|
| **① 长连接** | **Stream 模式**：官方定位为"推荐的事件订阅方式"，WebSocket 主动外连，不需要公网 IP / 域名 / 防火墙白名单 |
| **② 可更新消息** | AI 卡片流式更新（打字机效果），面向 AIGC 场景持续更新同一张卡片 |
| **③ 交互卡片** | 互动卡片；**卡片回调也走 Stream 模式**（三种回调同一条连接） |
| **④ @ 隔离** | 群聊中 @ 机器人的消息事件，和企微同构 |

## 与企微的差异（动手前必须知道）

1. **Stream 模式是"两步建连"。** 先 HTTP 换 `endpoint` + `ticket`，再建 WebSocket。
   这意味着 1 号适配点比企微多一次握手 —— 而"取 ticket 失败"是一个**独立的失败面**，
   要和"WebSocket 断了"分开报，否则重连逻辑会含糊。
2. **需要企业内部应用。** 个人开发者要先有组织。这是入驻门槛，不是技术门槛。
3. **卡片回调走同一条连接**，这是它的优势，但也意味着**回调延迟与消息延迟共享同一条管道** ——
   长任务堆积时要确认回调不会被饿死。

## 待实测（没打勾之前不写"支持"）

- [ ] Stream 连接稳定运行 24 小时，断网后能自愈，且**取 ticket 失败**能被单独识别
- [ ] AI 卡片的流式更新频率上限（太快会被限流，太慢像卡住）
- [ ] 按钮文字的实际长度上限
- [ ] 单条消息的字节上限，以及超限时的错误码形状
- [ ] 卡片回调与消息回调同管道时，前者会不会被后者的洪峰拖慢
- [ ] `/new` 之后模型拿不到上一轮内容（含本机会话存储）
